tessa：純 markdown 的 AI 多角色協作框架

發表於 2026-05-07 更新於 2026-07-12 分類於 個人專案 ， AI 文章字數： 3.2k 所需閱讀時間 ≈ 11 分鐘

為什麼會做這個

過去半年用 AI 寫程式，常常踩到三類問題：

  • 同一份需求，不同對話會給出不同的命名、錯誤處理、註解風格
  • 對話跑長之後 AI 會忘掉前面的決策，把砍掉的選項再拿出來提案
  • 同一個 AI 同時當作者跟審核者，幾乎不會抓到真問題

試過用更講究的 prompt 解，沒有根本性改善。試過換更強的模型，問題照樣在。

後來想通，問題不是出在 prompt 或模型，是出在工作方式：規劃跟實作混在同一段對話、審核跟產出由同一個身分做、決策紀錄散在 chat 歷史裡。這三件事只要任何一件還在，下一次合作還是會踩同樣的坑。

於是動手寫了一套東西，叫 tessa。

tessa 是什麼

tessa 是一套純 markdown 的 AI 多角色協作框架。把跟 AI 協作的流程拆成幾個固定角色：

  • planner：拆需求、列候選方案
  • planning_manager：審候選、決定採哪一條、退掉哪幾條
  • executor：照規格動手產出
  • qa：對照規格驗收
  • execution_manager：最後把關、抓 spec 沒寫到的洞

每個角色就是一份 markdown 檔，定義它的職責、紀律、輸出格式。沒有 runtime、沒有 SDK、沒有後台依賴，安裝後就是一份 .claude/agents/*.md（或對應 CLI 的格式），跑在你已有的 LLM CLI 上。

跨 CLI 支援 Claude Code、Cursor、Kiro 三個原生 adapter，加上 Anthropic Agent Skills 標準廣撒到 20+ 個相容 CLI。

跑一次完整流程是什麼樣

舉一個實際跑過的例子：為這套工具想名字。任務不是寫 code，是要為這一套小工具挑一個正式名字。最後拍板的結果就是 tessa 這個名字。

整個流程被拆成 6 段，依序跑：

  1. planner 出候選結構
  2. planning_manager 審候選
  3. planner 寫完整規格書
  4. planning_manager 審規格書
  5. executor 照規格產出
  6. qa + execution_manager 驗收

每段中間都有「審過才往下走」的閘門。

第二段 planning_manager 真的退回了我，說需求文件有兩個地方語意不夠精確，要先補完才接著跑。「主管」這個角色不是按按鈕、看一遍蓋章的，它真的會擋。

planner 出 4 條候選

planner 給的不是一條方案，是 4 條候選結構：

  • 每條附「吃哪幾個視角、弱在哪個視角」的論述
  • 對沒推薦的方案也寫同樣篇幅論述，不用「同上不採」帶過
  • 末尾列 RISK-FLAG，9 條風險旗標標出來請主管裁決
  • 其中 2 條是 planner 自己也沒答的開放問題

planner 不假裝自己什麼都想清楚。自承沒想清楚也是合法輸出，甚至是被鼓勵的輸出。一個會說「這個我還沒想清楚、請你決定」的 planner，比一個假裝什麼都想透了的可信得多。

好的提案不是給一個答案，是給一張包含取捨的地圖，再加一份還沒答的問題清單。

planning_manager 審了什麼

manager 做了 4 件事：

  • 對 planner 推薦的方案逐條對齊原始需求
  • 對沒推薦的另外三條方案各寫一段判斷論述，解釋為什麼不採
  • 跑 friction：強制找四種類型的反例（規格沒講的邊界、可疑假設、沒考慮的使用者情境、外部視角的關鍵問題）
  • 跑 bias 自承：明寫自己這次審核可能會傾向偷懶或過度找麻煩，給自己訂抵抗方法

那場 manager 抓了 8 條漏洞。其中一條是我把章節編號引用錯：我寫「§1.3 演進階段表」，manager 跨檔讀對方檔案後發現實質內容在 §3，不是 §1.3。沒有「大概看一下」就放過。

manager 的價值不在於蓋章放行，在於那 4 件事撐住了「真的有人在擋」這件事。

executor 寫稿時的紅線守備

規格書定下來之後，executor 拿著規格動手產出。規格書裡列了一份禁字面表：

  • 不可以寫某幾個競品名
  • 不可以提某幾個個人專案名
  • 不可以出現拍板的最後決定字面（命名審議當時還在進行，結果應該保留 placeholder）

executor 寫完一段就跑一次字面比對指令，確認禁區沒被踩到。寫到第三段時觸發了一條紅線：無意中提到了應該用 placeholder 代稱的名字字面。executor 沒等 manager 抓，自己跑檢查時就發現，回頭改寫了那三段，再跑一次驗證才往下寫。

紅線守備是字面 grep 機械可驗，不靠人記。從規格書把禁字面字面化、到 executor 寫完自跑驗證、到 manager 再抽查重跑，這條鏈是機械的，不靠任何角色「應該記得」。

紀律不依賴每個人的注意力，是寫進規格、跑得起來的。

qa + execution_manager 驗收

最後一段是 qa 跟 execution_manager 接手，把產出對著規格書的 AC（驗收條件）逐條跑。

那場 review 抓到一條規格書沒寫到的紅線：executor 交付的內容字面雖然沒踩禁區，但語意上等於暗示了一個應該用 placeholder 的東西。規格書原本沒涵蓋這種「字面安全但語意洩漏」的情境。

review 抓出來之後，這個發現被萃成一條經驗寫進團隊記憶。下次同類任務這條紀律會被自動帶進去，不需要再踩一次同樣的坑。

每跑完一個任務，留下的不只是成品，還有下一次會被帶進去用的經驗。

不只能寫 code

剛剛這個命名審議的任務本來就不是寫 code。tessa 在「為一套工具想名字」這種純語感、純判斷力的任務上一樣能跑。

我自己已經實際試過、跑得起來的非工程任務有三類：

  • 寫文章 / 內容企劃：從題目、到切入角度、到規格書、到初稿、到冷讀檢查。整條鏈跟工程任務形狀一樣。這篇文章本身就是這樣跑出來的。
  • 個人專案規劃：一週的工作排程、新功能的優先順序、學習路徑規劃。每次規劃都有「planner 丟候選、manager 挑、規格書定下來」的紀錄，一個月後回去看得懂當時為什麼這樣決定。
  • 知識整理 / 教材：把學完的主題整理成可以教別人的形狀、寫內訓教材、把研究筆記重組成長文。

三類都不是寫 code，但都吃同一套「規劃 - 審核 - 執行 - 品保」的形狀。

tessa 真正解的問題不是「怎麼寫程式」，是「怎麼跟 AI 做有結構的協作」。結構這件事，跟你做的是工程任務、寫作任務、規劃任務，沒有本質差別。

怎麼跑

下載一個資料夾，看看裡面那幾份 markdown 檔案，跟著 markdown 跑，就有一個結構化團隊。

這個資料夾裡裝的是：

  • 幾個角色的職責描述（markdown）
  • 幾個流程的步驟清單（markdown）
  • 幾條團隊共用的紀律規則（markdown）
  • 團隊共同的記憶檔（markdown）

每一份就是用人話寫的 markdown，看得懂就改得動，不滿意可以自己重寫。沒有要跑什麼程式、沒有要裝什麼後台依賴、沒有要付月費、沒有要登入什麼帳號、沒有 API key 要設。

tessa 不會自動幫你做事。它不是把你替換掉的東西，是給你一張合作對象清單跟合作流程。人類仍是 team lead、仍是最後拍板的人。planner 丟候選你看、manager 擋一次你看、executor 寫稿你看、qa 抓問題你看，最後決定要不要採納的人永遠是你。

它解的不是「讓 AI 自動完成」，是「讓 AI 用一個你看得懂、你能審、你能改的方式分工合作」。

自動化是把決策權交出去，結構化是把決策權留在自己手上但讓過程整齊。前者你失去掌控，後者你拿回掌控。

關於這篇文章

這篇文章本身是用 tessa 的內容創作預設（content-creation preset）跑出來的。從規劃結構、planner 丟候選、manager 審過退回兩次、規格書定下骨架、executor 照規格寫初稿、到 qa 抓字面，整套流程跟剛剛那個命名審議案例走的是同一條鏈。

這樣做是想驗證一件事：如果 tessa 真的有用，它在「為一套工具想名字」跟「寫一篇給開發者讀的長文」這兩個性質完全不同的任務上應該都跑得起來。如果只在工程任務上成立，「不只能寫 code」這句話就站不住腳。

跟 AI 協作的下一步不是更聰明的 prompt，是更結構化的工作方式。不用寫 code 也能讓 AI 幫你做有結構的協作。
