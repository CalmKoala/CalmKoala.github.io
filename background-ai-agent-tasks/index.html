哪些工作該交給背景 AI agent？

任務跑得久，不代表適合丟到背景

發表於 2026-09-05 分類於 學習筆記 ， AI 文章字數： 2.9k 所需閱讀時間 ≈ 10 分鐘

最近我在做一套能讓 AI agent 留在背景工作、完成後再把結果送回來的系統。最先拿來測試的，是一場多角色討論：先由一個角色找資料，其他角色從不同角度提出意見，最後再整理成結論。整個流程大約要跑 5 到 10 分鐘，中間也不需要我逐句回覆，看起來很適合丟到背景，終於可以假裝自己有員工了。

做到一半，我卻開始卡在一些和答案聰不聰明無關的問題。資料不足時，它要直接停下來，還是自己換個題目？其中一個角色失敗後，前面完成的步驟要不要重跑？我關掉對話之後，它跑完或卡住，又要用什麼方式告訴我？

本文所說的背景 AI agent，指的是工作開始後不再佔住目前的對話；我可以先去做別的事，等它完成、失敗或需要幫忙時再回來處理。那麼，一個任務預計要跑 10 分鐘，直接丟到背景就好了嗎？我實際做完才發現，執行時間只回答了我要等多久，還沒有回答它能不能在沒有人看著時繼續工作。

長時間不等於適合背景

背景執行可以省下等待時間，判斷仍得由人處理。Agent 跑測試、整理資料或查文件時，我可以回到原本的工作，不必盯著畫面等它交付。不過它也少了對話裡的即時往返；需求有一點模糊、途中出現新線索，或下一步牽涉取捨時，就不適合每次都停下來等我即時決定。

我現在會先用四個問題判斷：執行中還可能改需求嗎？完成與停止條件能不能核對？中途需不需要人選方向？失敗後能不能查到狀態並安全處理？只看「會跑多久」，很容易把一件仍需要來回討論的工作提早丟出去。

  START["準備交給背景 agent"] --> SCOPE{"執行中還可能改需求嗎？"}
  SCOPE -- "會" --> CHAT["留在對話裡"]
  SCOPE -- "不會" --> DONE{"完成與停止條件能核對嗎？"}
  DONE -- "不能" --> CHAT
  DONE -- "能" --> CHOICE{"中途需要人選方向嗎？"}
  CHOICE -- "需要" --> CHAT
  CHOICE -- "不需要" --> FAILURE{"失敗後能查到狀態並安全處理嗎？"}
  FAILURE -- "還不能" --> GUARD["先補狀態、通知或人工確認"]
  FAILURE -- "能" --> BACKGROUND["適合背景執行"]

先寫好完成與停止條件

前面的四個問題用來判斷任務要不要交到背景；決定交出去後，我才用下面幾項把工作內容寫完整。「幫我看看最近系統有沒有問題」很難直接交給背景，AI agent 不知道該看哪些資料、查到什麼程度才算完成，也不知道找不到證據時能不能停下來。最後即使交回一份看似合理的觀察，我也很難核對它漏了什麼。

如果改成「讀最近七天的錯誤紀錄與任務失敗統計，找出重複出現的問題；沒有足夠證據就回報資料不足；有的話整理成一頁摘要並附上來源，不要修改任何設定」，任務就多了幾個可以檢查的部分：要讀哪些資料、交回什麼、何時可以停止，以及哪些動作不能做。完成後再要求它回報結果或失敗原因，背景 agent 才知道自己要走到哪裡。

我現在交代背景工作時，至少會寫下五件事：資料範圍、交付內容、停止條件、不能執行的動作，以及完成或失敗後的回報方式。就算不懂複雜的 agent 架構，也能先把原本藏在對話來回裡的判斷寫出來。

背景任務可以停下來等人。資料不足時回報缺了什麼，比自己猜完再交一份完整答案更有用。

中途要選方向，就留在對話

同一種工作，有時適合背景執行，有時仍要留在眼前，差別通常在於下一步能不能事先決定。修 bug 就是常見的灰色地帶：如果錯誤已經可以重現、修改範圍固定，也有一組測試能判斷修好沒有，agent 可以在背景完成；如果連原因都還不知道，查到新線索後可能要跨服務修改，甚至牽涉產品行為，對話裡的即時判斷會比較省事。

工作 適合放到背景的情況 適合留在對話的情況
修 bug 已能重現，範圍固定，有測試可核對 原因未知，途中可能擴大修改範圍
查資料 資料來源與比較項目已指定 還在找問題，結果會改變研究方向
批次改檔 改法一致，可用檢查或測試驗收 每個檔案都可能需要不同取捨
寫文章 格式、錯字與既定規則檢查 主題、例子與語氣還在來回調整

這也不必硬分成「全程背景」或「全程對話」。一份探索工作可以先在背景蒐集證據，遇到岔路時停下來請人選方向，再把選定的部分交回背景執行。把人的判斷點切出來，可以分開處理探索與執行，也比較好管理。

看得到狀態，才敢離開

我的第一版會保存已完成的調查與各輪討論，遇到部分預料內的成功或失敗情況，也會更新紀錄並嘗試通知。不過我回頭檢查程式才發現，如果整場討論撞到最外層的 10 分鐘上限，內部雖然會產生失敗結果，背景入口目前沒有把它轉成通知，先前建立的討論紀錄也可能還停在「執行中」。工作已經停了，畫面看起來卻像它還在跑。

這個落差在同步對話裡很快就會被看到，放到背景後卻可能隔很久才發現。通知只能提醒我回來，系統還要留一個能查詢的地方，至少分得出「等待執行、執行中、已完成、失敗或逾時、等待人處理」。理想情況下，就算訊息沒有送達，我仍能靠任務編號回來確認；程式重新啟動後，也能找出上一次沒有收尾的工作。

如果你主要用現成的 AI 工具，不需要先做一套狀態系統，但可以留意三件事：離開頁面後任務會不會繼續、失敗時能不能查到原因，以及它需要你做決定時會停在哪裡。少了其中一項，背景執行很容易變成「晚一點回來看看有沒有結果」。

外部動作不要直接重跑

背景工作遇到網路中斷、工具逾時或使用額度限制，重跑看起來是最直接的處理方式。讀檔、查資料、跑測試通常可以再做一次；寄信、建立排程、發版或修改正式環境就要小心，因為第一次可能已經成功，只是結果來不及傳回來。

重跑前，我會先確認前一次是否完成外部動作。單靠本機留下一筆「做過了」的紀錄仍有空隙，外部動作可能已經成功，程式卻在存好紀錄前中斷。如果一定要自動重跑，外部服務還得能用固定的請求編號辨識同一筆操作；工程上常把這種重複執行不影響結果的設計稱為「冪等」。做不到時，我會讓背景 agent 只準備資料或草稿，寄出、部署或寫入仍交回人確認。這和我在上一篇談多 agent 的文章遇到的重複執行問題相同，只是沒有人盯著時更難察覺。

回到一開始的多角色討論，我願意把它放到背景，10 分鐘的執行時間只是次要理由。它要讀的資料、討論輪數與輸出格式都已經固定，找不到合適的題目也可以停下來；最後交回的是建議，不會直接替我改資料或發布內容。至於最外層逾時後的狀態與通知，我還得補完，否則它只能算「會自己跑」，還不到我能放心離開的程度。

我現在準備把工作交給背景 agent 前，會先寫出它要讀什麼、在哪裡停、怎麼回報，以及做過的動作能不能再來一次。這幾件事寫不出來，我就繼續留在對話裡。等待久一點有點煩，回來後才發現它卡在一個沒人知道的地方，顯然更煩（？）
